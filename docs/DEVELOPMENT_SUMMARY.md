# Development summary

## Process and architecture

The provided specification, database, API, and UI documents were the starting point. An initial review identified decisions that needed to be settled before implementation, including public slugs, access to closed surveys, instructor authorization, and the race between closing a survey and submitting a response. Those decisions became the shared contract in `docs/DECISIONS.md`, including RPC signatures, data types, routes, error codes, and file ownership. The contract also limited editing to drafts so that later changes would not alter historical results.

Claude Code wrote prompts and reviewed the work, acting as the prompter on my behalf. Codex CLI using `gpt-6.1-terra` implemented the application in parallel chats. The scaffold and database were separate workstreams; dashboard, editor, student, and presentation/results pages then had their own files. Separate chats also handled documentation and test scripts. The shared contract and ownership map reduced conflicts in the shared working tree. Claude reviewed diffs, ran checks, and exercised the application in a browser, then sent follow-up prompts where needed. Codex made the commits when asked. The prompt log records the turns and review findings; full command event streams remain outside the repository.

The frontend is a React and TypeScript single-page app built with Vite. Supabase Auth supplies the instructor session, and PostgreSQL stores surveys, questions, choices, responses, and answers. Instructor table reads are protected by row-level security; all writes go through database RPCs. The database checks the instructor role in trusted `app_metadata`, not just the frontend route guard. Anonymous users have no direct table privileges and use two public RPCs to load and submit a survey. The submission function validates the answers and writes the response atomically. A browser token and database uniqueness constraint help prevent accidental repeat submissions, but do not establish a student's identity.

## Testing and findings

Testing combined automated checks with use of the deployed application. The Vitest suite passed 26 tests. The local Docker database harness passed 62 SQL checks and six concurrency checks; the same 62 SQL checks and 31 HTTP-level RLS checks passed on the live Supabase project. A live load test sent 200 simulated students from one machine to load and submit at once. All succeeded, with load-to-confirmation times from 349 ms to 4.3 seconds and a 4.0-second 95th percentile. It also checked result tallies, export rows, and duplicate-token rejection. This was one measured workload, not proof of capacity under every condition.

The deployed browser pass covered instructor survey creation, validation, saving, reordering, activation and its warning, presentation and live count, closing, duplication, archiving, status filtering, and deletion with its response-count warning. It covered student validation, submission and the already-submitted, closed, and not-found states in desktop Chrome. A phone submission used the QR code. The Supabase Table Editor and application results screenshots document a test survey and its stored data.

Review found issues that passing checks alone would have missed. The first anonymous write probes used invalid IDs, so they could pass because of malformed input rather than denied access. The revised probes use valid random IDs and require PostgreSQL permission-denied code `42501`; a successful zero-row update is a failure. An intermediate revision unnecessarily required a hand-built fixture, which was removed after reviewing how privilege checks work.

The first deployed browser pass found that `getSurvey` returned `PGRST108`: the query embedded questions and choices both as counts and as rows, and PostgREST associated nested ordering with the count embeds. The fix gave the row embeds distinct aliases and ordered by those aliases; it was checked against the live project, including the pagination fallback. Unit tests had missed the issue because they mock Supabase, and page review had preceded the live database.

After a deployment, an already-open page could request an obsolete lazy-loaded chunk. Cloudflare's SPA fallback returned HTML for the missing chunk, the import failed, and the page went blank. The app now handles Vite's preload error with a limited reload and has an error boundary with a reload control; the fix was tested with a removed chunk in a production build. Results presented another browser-only problem: the counts were correct but chart bars were empty. Adding a hidden category Y axis gave each vertical bar a position, and a headless Chrome test checked its width. That test skips if Chrome is unavailable.

Before the first deployment, a local `wrangler pages dev` run showed that the scaffold's `/* /index.html 200` rule in `public/_redirects` was ignored as an infinite loop. Removing it retained direct-route handling because Pages serves `index.html` for unknown paths without a top-level `404.html`. A confirmation dialog appeared in the upper-left corner because Tailwind's reset removed the browser's default auto margin; restoring that margin centered it.

## What worked and limitations

The explicit contract made parallel implementation practical: page chats could work independently against the same API and avoid editing one another's files. Separate review and follow-up prompts caught problems in generated code and even in the tests themselves. The real database and deployed browser checks were particularly useful because mocks and code review could not reproduce every integration or rendering failure. Parallel work still required coordination, especially around shared files and sequential commits, and early approval of a page's code did not replace testing it against the deployed backend.

The app is designed for one instructor and one active survey. It does not use Supabase Realtime: results refresh on request and the presentation count polls while visible. Browser-token duplicate protection can be bypassed by clearing storage or using another device. The load test came from one machine, and the manual browser pass described above does not establish behavior across every browser or device. The deployment and database require their own configuration; instructor credentials are supplied privately rather than stored in the repository.
